## 1. 立项判断

建议以现有原生 macOS 应用为基础，继续建设一个免费开源、只录系统声音、结果可验证的小工具。保留现有 Core Audio process tap（进程音频采集）、ALAC（Apple 无损音频编码）、本地处理和资源释放机制，不另建应用骨架。

面向用户的一句话：

> 录下 Mac 正在播放的声音，保存为无损音频，并查看实际文件的编码结果。

技术和隐私边界作为可信依据：不含麦克风录制路径、不建立屏幕捕获会话、不安装第三方驱动、不上传录音。不能用 ALAC 标签承诺与播放器源文件逐位相同，也不能承诺恢复音源已经损失的信息。

立项理由是已有可运行的技术基线，值得以有限投入验证用户是否需要这种简单、明确的工具。现有竞品研究不能证明需求规模、获客能力或付费意愿；暂不把商业化作为首期目标。

## 3. 目标用户与待验证需求

优先服务偶尔需要保存 Mac 播放声音、希望无需配置音频路由的个人用户，例如保存自己制作的音频演示、软件提示音或可录制的试听片段。

核心任务：开始录制 → 停止 → 保存 → 确认文件可用。

首轮需要验证三个假设：

1. 用户能独立完成录制和保存，并理解系统音频权限文案。
2. 用户关心不录麦克风和文件实际编码，结果说明能消除疑虑。
3. 全系统录制足以覆盖其任务；其他应用的提示音不会频繁使录音报废。

这些是待验证假设，不是已经发现的用户需求。专业混音、会议转写、麦克风录制和音频素材库不纳入首期。

现有替代路径包括虚拟声卡配合录音软件、专业音频工作台及轻量系统录音器，详见原竞品研究。差异化假设是“免费开源、简单操作、明确隐私边界、可检查输出”这组体验有价值；单项技术和 ALAC 本身不构成独有优势。

## 4. 首期产品范围

首期目标：把已经存在的录制能力变成用户能够理解和核实的交付结果，同时保持可靠停止、释放和退出。

### 必须完成

| 项目 | 预期行为 | 验收标准 |
| --- | --- | --- |
| 文件结果信息 | 停止并生成临时文件后，读取实际文件，显示编码、采样率、声道、时长；保存后显示最终文件大小和位置 | 展示值来自文件探测；最终位深无法可靠读取时显示未知或省略，不能套用 24-bit 编码提示 |
| ALAC 验证状态 | 实际音轨确认为 ALAC 才显示“已验证为 ALAC” | 非 ALAC、缺失音轨、文件不可读分别给出清楚的状态；验证异常保留可用文件与再次导出入口 |
| 状态边界 | 区分“录制已停止”“临时文件已生成”“文件已保存”“编码已验证” | 取消保存不能显示保存成功；编码验证不能暗示录音含有声音或采集资源已释放 |
| 简明说明 | 在合适位置说明只录系统声音、本地处理及无损含义 | 文案与实现一致；不将系统权限分类误写成屏幕内容被采集 |
| 生命周期回归 | 延续现有停止、取消、窗口关闭和退出行为 | 原有测试通过；真实录音可解码；停止后 tap/device/IO 释放；退出路径结束进程 |

文件编码验证不等于逐位无损证明、完整性证明或有声检测。静音也可能是合法录音，不能仅凭峰值为零判定编码失败。

### 不阻塞首期的小范围后续项

- 可选 JSON 元数据文件：包含编码、采样率、声道、时长、文件大小、应用版本及最终保存文件的 SHA-256（文件校验摘要）。明确它用于识别同一文件，不证明音源真实性。无需为验证结果默认多生成一个文件。
- 独立产品页和简短真实操作演示：先形成可审阅的本地内容；公开发布作为单独交付步骤。
- M4A 容器可行性和播放器兼容性验证：先验证 ALAC 封装与常用播放器行为，再决定是否调整默认格式；不要只改扩展名。

### 暂缓

单 App 录制、菜单栏、全局快捷键、暂停恢复、波形剪辑、文件历史、多格式、转写、账号、云端及 App Store 分发。单 App 录制仅在全系统杂音被反复证实为阻碍后提升优先级。

## 5. 可靠性优先级

用户能保住录音比展示更多技术字段更重要。下一步实现前先梳理保存失败、长录音和中断时的文件行为；若发现会丢失已录内容的高概率缺陷，优先处理，再推进结果展示。

| 验证项 | 判定要求 | 所需证据 |
| --- | --- | --- |
| 现有主流程 | 开始、取消倒计时、停止、取消保存后再次导出、再次录制、窗口关闭、⌘Q 符合说明 | 本机操作记录、可解码文件及资源状态 |
| 保存失败与磁盘不足 | 明确报错；可保留的临时音频不被误删；可重试时提供入口 | 可控失败实验；不得以填满用户系统盘来制造故障 |
| 长时录音 | 建议至少 60 分钟，记录内存、文件增长、最终时长和解码结果 | 独立运行记录；通过前不宣传无限时长 |
| 休眠、唤醒与设备切换 | 不悬挂、不静默宣称成功；中断时明确说明实际保留范围 | 蓝牙 / USB / HDMI 等分项实测记录 |
| 权限撤销与异常退出 | 明确失败行为及文件保全边界 | 独立实验；恢复能力未实现前不作承诺 |
| Intel 与 macOS 14.2 | 对应环境完成录制、保存和退出 | 真机或适用的独立系统环境；构建不能替代 |

缺少外设或目标硬件时标记“待验证”，允许有限范围试用，但不扩大已验证兼容性的宣传。

## 6. 推进顺序与完成条件

1. **立项基线（本稿）**：明确继承资产、用户假设、首期范围和验证边界。
2. **实现前审查**：阅读当前源码和测试，确定文件探测、结果展示及失败保全的接入点；按现有结构做最小增量。未经检查不估算具体开发工期。
3. **首期实现与本机验收**：完成结果信息和验证状态，执行受影响测试及真实录音回归；保留当前安装版本，使用隔离测试构建。
4. **小范围使用验证**：建议邀请 5 位目标用户完成至少一次真实任务；通过用户同意的观察或反馈收集结果，不加入后台遥测。
5. **发布判断**：核对实际安装包、签名公证、下载入口和兼容性表，再决定公开发布的范围及文案。

试用的初步通过标准：至少 4/5 用户无需指导完成保存；没有未解释的录音丢失或退出清理故障；用户能够理解全系统录制范围及“ALAC 无损”的含义。这是决策阈值提案，小样本通过不代表市场需求已成立。

若主要障碍是保存失败或丢录音，优先修可靠性；若其他 App 杂音重复阻碍任务，再评估单 App；若验证信息无人使用，收简呈现，不据此堆叠更多元数据功能。

## 7. 初始立项交付边界

选用基建：沿用现有 Swift 应用、Core Audio 采集、ALAC 封装、构建签名脚本及测试机制；文档采用仓库的轻量产品简报方式。不新增账号、云端、支付或 AI 服务模块。

待定项集中记录：源码审查后确定文件探测实现及工期；用户试用后决定格式调整和单 App 需求优先级；获得对应环境后安排 Intel、最低系统与外设验证。这些待定项不阻塞本稿，但相应证据缺失时不能声称已经实现或通过。

## 8. 用户新增方向 · 2026-09-14

### 音乐文件获取场景

已完成[渠道与搜索意图调研](music-download-research-2026-09-14.md)。现有证据支持“用户需要可在其他软件使用的音频文件”这一待验证方向，不代表关键词搜索量、Mac 用户规模或购买意愿已经成立。

优先补录制结果导入目标剪辑软件的实际验证，再决定格式优化与单 App 功能。录音工具不等于版权授权渠道，也不承诺得到母带或分轨。原有“可验证 ALAC”保留为可信依据，不替代用户任务表述。

### 无账号自动更新与后续触达

用户明确要求复用浩宇的更新能力，故解除初稿的自动更新暂缓限制。实现沿用 Sparkle（macOS 应用更新框架）的检查、签名验证和用户确认安装机制，使用录音机独立的更新清单与公钥；参见[接入说明](auto-update.md)。

产品约束：

- 录音无需账号；自动检查由用户选择，手动检查入口保留。
- 录音处理保持本地；更新检查、更新说明和安装包下载需要联网，不能继续对新版本宣称“完全不联网”。不上传音频、不添加行为遥测。
- 新版本可在更新说明中介绍新增功能，包括未来可选的登录或付费能力；本轮不实现账号或收费。
- 检查更新需要应用运行、用户允许相应检查且联网。用户可不升级；它不是向关闭应用强制推送的通道，也不是所有下载用户均可触达的保证。
- 现有不带更新模块的 3.0 用户需要手动安装一次带更新能力的版本。不能追溯远程启用。
- 正在准备、倒计时、录音、导出或有未保存片段时，更新不得触发丢弃录音的退出；安装前及最终退出都要验证。
- 本机接入与正式发布分别验收：独立正式清单、公钥、签名安装包、可访问下载以及真实旧版到新版安装链完成后，才可声称远程自动更新可用。
