# 3.0 录制生命周期修复 · 2026-09-14

## 原因与证据

旧版通过 ScreenCaptureKit 创建显示器共享会话，只注册音频输出。启动尚未返回时取消/退出可能与启动交错；先等待启动任务再停止采集会互相等待。后续 2 秒强制退出补丁只证明进程退出，不能证明系统会话释放。

本轮线程采样进一步复现：Swift 主线程任务调用 NSApplication.terminate 后，terminateLater 进入 _shouldTerminate 的嵌套事件循环，计划在 MainActor 上执行的清理/回复任务未执行。修复前应用悬挂，修复后相同的程序化退出和窗口关闭路径通过。

界面验收也会干扰紫色标记：系统日志显示截图工具另建了 multi-window 屏幕会话，audioEnabled=0、micEnabled=0，与新版音频 tap 分开。结束界面验收后，系统日志确认 stopAndInvalidate、stopWithError、streamDidStop、hasStarted=0，后续观察没有该活动会话的健康计数。不能仅凭图标或进程不存在判定录制状态。

旧版触发的全部 macOS 内部残留原因无法由现有脱敏日志确定，不统称为系统缓存或操作系统缺陷。

## 修复

- 删除屏幕采集、显示器枚举、CG 屏幕权限预检查，使用公开 Core Audio process tap API。
- actor 按顺序管理 prepare/start/stop/cancel；同一个所有者逆序销毁私有 tap、聚合设备和 IO 回调。
- 停止 IO、排空音频队列后才封装 MP4，避免写入与清理交错。资源释放失败明确报告并保留句柄以重试。
- 退出先返回 terminateCancel，正常事件循环完成清理后再次 terminate 并返回 terminateNow；移除未确认清理就退出的定时器。

## 验收

Apple Silicon、macOS 26.6.2，7 项自动测试通过。三轮真实系统提示音均生成 ALAC MP4，48 kHz / 双声道，解码峰值约 0.0595，确认不是空轨或全零静音。每轮停止及连续取消后 tap=0、device=0、io=none、running=false；程序化验收随后自行退出。

真实按钮操作通过：开始、3 秒倒计时、计时、停止并保存、再次录制、录制中关闭最后一个窗口。手工验收 MP4 解码时长 24.448 秒，含真实声音。验收录音、原始机器日志与路径留在本地。

通用二进制包含 arm64 / x86_64；Intel 硬件、最低系统、所有外设及录制中切换设备没有在本机验证。
